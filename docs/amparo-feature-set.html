Amparo Feature Set

The open agent that acts under policy — what it ships today, and how that differs from every other kind of agent software.

v0.3.0 pre-alpha Apache-2.0 Rust 9 crates 298 tests

What Amparo is

Amparo is an assembled agent, not a framework: a single Rust binary that runs a real tool-use loop — files, shell, git, web, tests, build — where every tool call passes a policy check before it executes, and the model driving the loop is yours to choose. It runs headless as a CLI, an MCP server, or a chat bot for Telegram, Discord and Slack, serving many users at once with per-user policy, per-user trust ceilings, per-user workspace directories, and requester-only approvals.

Three commitments shape every design decision:

  • Bring your own LLM. Anthropic, OpenAI, or any OpenAI-compatible endpoint (Ollama, vLLM, OpenRouter, Together, Groq). No bundled model, no required sidecar.
  • Policy is an interface, not a product. The gate between “the model decided to do this” and “this ran” is an open wire protocol. The default is deny.
  • Deployable anywhere. A standalone server, a container, a systemd unit, a chat bot — not welded to a desktop session.

The gate chain — the spine

Every tool call the model makes passes through four gates in order. If any gate says no, the call does not run — and the model still gets an answer for it:

Registry lookupunknown tools get an honest error, not a hallucinated result
Trust ceilingtiers: Observational · LocalMutating · ExternalEffector · SystemControl
Policy enginelocal allow/deny engines, or a remote engine over the open wire spec
Human approvalinline Approve/Deny buttons, 60 s auto-deny, requester-only presses

Executed → the result goes back to the model as a tool_result. Blocked → a blocked-call answer still goes back, carrying the same tool_call_id — the loop never stalls, and the model never fills a gap with invention.

The full feature set

Grouped by the layer that owns it. Everything below is in the tree and behind the gate today.

Inference M1

  • One InferenceProvider trait; two providers: OpenAI-compatible (any endpoint, incl. an Ollama-native branch) and Anthropic-native (Messages API, tool_use/tool_result translated to the same contract)
  • Fail-closed: no silent localhost default — URL and model are required
  • Per-request and stream-idle timeouts, max_tokens clamp, optional model allowlist
  • Configurable base URL — works with local sidecars and hosted APIs alike

The agent loop M2

  • Native tool_calls — no text-parsed ReAct, no format guessing
  • Max steps + conversation trimming, parallel tool batches with retry ×2, the one-shot shortcut, a same-tool loop guard, empty-turn recovery
  • Self-verification: every final answer is graded VERIFIED/INCOMPLETE before it ships
  • Events flow through an EventSink seam — the same [tag] progress lines on every surface

Policy M2b

  • PolicyEngine trait; deny-all default; AllowAllPolicyEngine is an explicit named opt-in, never the default
  • WirePolicyEngine: the open POST /check {tool_name, target} protocol, with the caller contract — never block on enforced:false, engine errors escalate, escalate means ask a human
  • Per-task session tags: checks carry session_id = "platform:user_id"

Tools M2c

  • 17 tools: 5 filesystem, shell (run_command), 6 git, run-tests, run-build, web search, fetch URL, memory search
  • Each carries a trust tier that drives the approval gate
  • 14 are workspace-bound: every path resolves under the workspace root, per user, via explicit PathPolicy injection

MCP, both directions M2e

  • McpServer: JSON-RPC 2.0 over stdio; a policy engine is a required constructor argument; every tools/call runs the same gate chain
  • McpClient: spawns external servers, handshakes, mounts their tools at ExternalEffector — remote tools cannot skip approval
  • Race-free pending map, 60 s call timeout, clean EOF draining

Memory & privacy M2a

  • Memory is an interface with a built-in default store; Engram is the recommended backend, never a dependency
  • Per-turn PII strip/restore (Secure Minions, per-message placeholder namespaces) — nudges and verification prompts are stripped too, so PII never reaches the self-verification context
  • Blocked/allowed domain routing for web tools

The chat face M4

  • Telegram (long polling), Discord (gateway websocket, resume-first reconnects), Slack (Socket Mode, echo-suppression) — hand-rolled, no platform SDKs
  • One task per chat (busy claim), panic containment (“The task crashed” instead of a dead loop), final answer delivered directly, never lost in a sink
  • Atomic approval router — a second press can never double-decide
  • Inline Approve/Deny buttons, 60 s auto-deny, single-message outcome edits

Multi-tenant identity M5

  • A TOML tenant directory: [users."platform:user_id"] sections; no entry = refused, fail-closed
  • Per-user trust ceiling (falls back to --trust-ceiling)
  • Per-user workspace under the root (users/<platform>-<user>/ by default); absolute and .. paths rejected at load and re-checked per task
  • Requester-only approvals: anyone else pressing the buttons gets a polite toast; the pending approval is never consumed
  • Legacy flat AMPARO_CHAT_ALLOWLIST path preserved

Operations & quality

  • One binary: amparo run / mcp-serve / chat telegram|discord|slack / version
  • stdout carries the final answer only — progress, gate decisions and reports go to stderr, so amparo run scripts cleanly
  • rustls-only — openssl-sys is out of the graph, cargo install needs no system OpenSSL
  • MSRV declared at Rust 1.85, verified on 1.98
  • Two gates, zero warnings: cargo test --workspace (298 tests incl. binary-level e2e) and cargo doc --workspace --no-deps with missing_docs on every crate

Against frameworks

LangChain, LangGraph and the OpenAI Agents SDK are scaffolding: the loop, the tools and the safety are your code. That is their superpower — and their gap. Amparo ships the boundary as the product: the gate chain is not a callback you register, it is the spine the loop is built around, and the policy engine behind it speaks an open protocol, so the operator can swap in any engine (including Guardrail, the commercial implementation) without touching the agent.

Against coding harnesses

Claude Code and OpenHands are outstanding at one human in front of one machine, with permissions as interactive session prompts. Amparo is built for the other job: one agent serving many humans over chat platforms, with identity, isolation and approval that hold up unattended. A harness’s permission model is a conversation with its user; Amparo’s is a policy decision with a session tag, a trust ceiling and a workspace directory attached.

Against autonomous agents

The AutoGPT generation proved demand and mostly proved the failure mode: a text-parsed loop with prompt-level guardrails, running until it ran out of tokens. Amparo keeps the useful loop mechanics (retries, trimming, self-verification) but replaces the text parsing with native tool calls, and replaces the prompt guardrails with a runtime gate that answers the model even when it blocks — so a blocked call can never turn into a hallucinated result.

Against guardrail tooling

NeMo Guardrails and Guardrails AI validate what goes in and out of a model — content and structure rails. Amparo gates what the model does: the tool call, before execution, per user. The layers are complementary; only one of them has an open wire spec an operator can implement in any language, which is the part Amparo owns.

Against memory products

mem0 and Letta are memory-first. Amparo treats memory as an interface with a default store and recommends Engram as the durable, syncable backend — the same pattern as policy: the product is the seam, not the store.

Against its own source

Amparo’s loop descends from Axiom-OS (MIT, provenance in NOTICE). What came across: the loop mechanics. What did not: the desktop compositor, screen ingestion, the companion loop, and the proxy coupling — and critically, the gap Axiom left between “the model asked” and “it ran.” Amparo’s reason to exist is that gap, closed with a gate chain and shipped as a headless, installable, versioned binary.

Against Hermes Agent

Hermes Agent (Nous Research, MIT, 2026) is the closest open-source peer in ambition: a self-hosted general agent with a messaging gateway, BYO models, persistent memory, and a self-improving skill system. The bets differ. Hermes wins on breadth and self-evolution — more platforms, sub-agents, cron, voice, and a Curator that distills successful runs into reusable skills. Amparo deliberately does not self-modify: its loop is deterministic and gated, because a shell-executing agent that rewrites its own playbook is harder to audit. The architectural fork: Hermes authorizes with static per-user permission levels; Amparo gates every call through a policy engine behind an open wire protocol, with a human-approval channel, attributed presses, per-user workspace confinement and session-tagged audit records. Authorization says who may; policy says what may, per action, with a record. Memory: Hermes ships rich built-in episodic and procedural stores; Amparo treats memory as an interface (Engram recommended). Deployment: Hermes is a Python stack; Amparo is one rustls-only binary. The honest summary: Hermes is the agent that grows with you; Amparo is the agent you can prove was acting under policy.

What is genuinely unique

  • Deny-by-default as the spine, not a setting. The trust-ceiling → policy → approval chain runs on every call, on every surface — CLI, MCP, chat — because all three surfaces share one gate contract.
  • The blocked-answer guarantee. An agent whose gate waves everything through is worse than one with no gate, because it looks safe. Every call — executed or blocked — gets a tool-role answer with its tool_call_id. The model can never stall or invent past a denied call.
  • Policy as an open wire spec. POST /check is documented, engine-agnostic, implementable in any language. The OpenTelemetry play: the protocol is free, the commercial engine (Guardrail) is optional, the agent works with either.
  • Multi-tenant by design. Open-source agents are almost uniformly single-operator. Amparo ships a tenant directory, per-user policy session tags, per-user trust ceilings, per-user workspace directories and requester-only approvals — the set of properties that makes a shell-executing agent safe to give to other people.
  • Approval as an attributed, first-class channel. Inline buttons on three platforms, an atomic router, a 60-second auto-deny, and strict press attribution: only the user who started the task can decide it.
  • Privacy inside the loop. PII is stripped before the verification step and restored after — the loop’s own introspection never sees personal data it has no business seeing.
  • One rustls-only binary, zero system deps. No Python venv, no Node, no OpenSSL headers. Install from source with one cargo command; run it anywhere.
  • Apache-2.0 with a provenance trail. The patent grant matters for software that executes arbitrary code, and NOTICE says exactly what came from Axiom-OS.

Honest trade-offs

  • Not kernel-level sandboxing. The boundary is workspace confinement + policy + approval. Running the chat face inside a container or VM is the operator’s job — and recommended for strangers.
  • One agent, not a swarm. No built-in multi-agent orchestration; multi-agent setups are an MCP composition problem, not a flag.
  • No bundled model. Bring-your-own is the commitment — it means configuration up front.
  • Pre-alpha. 0.x semver: APIs can break between minors. The repository is not yet public.
  • Config is read once. Tenant changes need a restart; no hot reload.
  • The policy engine must be reachable. In wire mode, checks are HTTP; the caller contract escalates to a human if the engine is down.
  • Session tags carry the platform id. Per-user policy means the engine sees platform:user_id with every check — inherent to the design; the operator chooses the engine.
  • English-first docs. The code is documented to ship, not yet translated.

The ecosystem around it

Amparo is the open agent; the rest of the stack stays optional and behind seams:

  • Guardrail — the commercial policy engine: a firewall for AI agents that act. A commercial implementation of the same open wire protocol Amparo checks against. Recommended, never required.
  • Engram — the memory backend: durable, private, syncable. The recommended implementation of Amparo’s memory interface. Recommended, never required.
  • The wire spec — POST /check {tool_name, target} → {verdict, reason, enforced}, published openly so anyone can build an engine.
